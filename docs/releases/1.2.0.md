# 1.2.0

iconbench on GitHub Pages: the same page, at an address, with nothing to install
and nothing running behind it. Pages serves files and does nothing else, and
iconbench's library was a server's folder — so this release is about what stands
in for the server when there is none.

Served by `npm start` or Docker, nothing has changed. The file format is the one
it was.

## How it works

### A library in the browser

- Where no server answers, **the library is kept in the browser's own storage**
  for the site. Packs, palettes, saving, renaming, deleting, the thumbnails in
  the pack panel — all of it works as it does at home.
- What stands in for the server is a **service worker**, `app/sw.js`. It answers
  `api/files` — get, put, delete and list, the four calls the page has always
  made — out of IndexedDB. The page's own code for reaching files did not
  change, and an icon's thumbnail is still an `<img>` pointed at the API. That
  the file API was kept plain enough for S3 to stand in for it is what let a
  browser stand in for it instead.
- The other way was a second backend inside `files.js`, calling IndexedDB
  directly. It would have worked in older browsers, but every thumbnail would
  have become a blob URL to make and to revoke, and `files.js` would have stopped
  being a mirror of the server. It was turned down.
- **The page finds out for itself.** The first thing it does is list the
  library, and the server answers a listing whatever is in it — so a 404 is a
  host with nobody home. Only then is the worker registered, and the listing
  asked again. Served locally the worker is a file in the folder that nothing
  ever starts, and start-up costs not one request more than it did.
- **What may be kept is decided once.** The rules the server held — an icon is
  `packs/<pack>/<icon>.svg` with a tidy name, under a megabyte, carrying no
  script — moved into `app/js/filerules.js`, and the server and the worker both
  ask them. The worker's handler, `app/js/fileapi.js`, speaks the web's own
  Request and Response, which Node has too, so `npm test` puts it through the
  very checks the real server gets, word for word.
- A stored SVG is served by the worker under the same policy as by the server:
  a drawing, that can do nothing.
- The worker keeps the library and **only the library**. The app's own files go
  to the network untouched, so the Pages copy does not open offline — the app
  has no hashed file names, and a copy of it kept by a worker would be a stale
  one sooner or later.
- A worker outlives the visit that registered it. Should one ever be left on an
  address that a real server later answers, it would sit in front of the real
  library, quietly keeping icons in the browser that were meant for the folder
  on disk. So each time it is started it looks once for a server, and if one is
  home it takes itself away.
- It needs a browser that runs a service worker written as a module: Chrome and
  Edge 91, Safari 16.4, Firefox 147.

### Saying so

- A library in the browser is **as easy to lose as a cookie**: it is one
  browser's, on one machine, and clearing the site's data deletes it. Nothing
  else about the page would let on, so the footer does — *Library kept in this
  browser*, in its right-hand corner, only where that is true. Its title has the
  rest: what the browser has and has not promised, and that **Save pack to…** is
  the backup.
- A footer note was chosen over a dialog on the first visit, which would say it
  once and leave nothing on the page afterwards to remind anyone.
- After the first save the page **asks the browser to keep the library for
  good** — not before, when there is nothing to lose. Chrome answers for itself,
  by how much the site is used; Firefox puts the question to the person. Either
  way the footer's title says where things stand.

### The copy in `docs/`

- Pages publishes a branch's root or its `docs/` folder and nothing else, so the
  app is **copied into `docs/app/` and committed there**: `npm run build:pages`.
  `docs/index.html` sends a visitor on to it, and `docs/.nojekyll` tells Pages to
  serve the folder as it is.
- The copy is **byte for byte**. Everything Pages needs lives in `app/` itself,
  so the script is `cp` and nothing cleverer — the repo still has no build step
  in the sense that matters: nothing is transformed, and what the browser loads
  is what was written.
- It is **rebuilt when a release is cut**, not on every change. What Pages shows
  is the last release, and a day's work in `app/` shows up once in a diff to
  review rather than twice. The cost is that nothing but habit guards a forgotten
  rebuild, so it is written into the release steps.
- Publishing `app/` straight from an Actions workflow was the other way, with no
  copy to go stale. The committed copy was the owner's call, over that: there is
  no workflow to keep, and what is on the site is what is in the folder.

## Known gaps

- An SVG drawn elsewhere cannot be edited, only traced.
- A sketch does not outlive its tab, and does not travel between machines.
- Palette edits are not undone by Ctrl+Z. The palette is the pack's and outlives
  the icon's history; **Reset to defaults** is the way back.
- On Pages the library does not travel either: it is one browser's. **Save pack
  to…** and **Load pack from…** carry a pack to another.
- The Pages copy does not open without a network.
